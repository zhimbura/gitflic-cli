# gitflic CLI — найденные баги

Лог багов, замеченных при реальном использовании CLI. Заполняется по ходу работы,
затем передаётся на исправление. Каждый пункт — с командой воспроизведения,
ожидаемым/фактическим поведением и предполагаемым местом в коде.

Формат записи: `BUG-NNN` (сквозная нумерация), severity, статус (`open` / `fixed`).

---

## BUG-001 — `mr diff` не декодирует HTML-entities из API (диффы нечитаемы)

- **Severity:** High (ломает основной сценарий — чтение диффа в код-ревью)
- **Статус:** ✅ FIXED (2026-06-22) — добавлен `htmlUnescape()` в `lib/format.mjs`, применяется к `ln.body` и заголовкам ханков в `printChanges()` (`lib/cmd/mr.mjs`). Однопроходный маппинг (`&amp;` декодируется без двойного прохода). Покрыто тестами в `lib/__tests__/format.test.mjs`.
- **Найдено:** 2026-06-22, при ревью `mne17let/zloysport` MR #45
- **Версия/бинарь:** `~/.local/bin/gitflic` → `gitflic-cli/bin/gitflic` (Node ESM, `lib/gitflic.mjs`)

**Воспроизведение:**
```bash
gitflic mr diff 45 --project mne17let/zloysport | head -20
```

**Фактически:** строки кода выводятся с HTML-экранированием:
```
+     implementation(project(&quot;:core:logger&quot;))
```

**Ожидается:**
```
+     implementation(project(":core:logger"))
```

**Диагностика:** entities приходят уже из GitFlic API. В raw-ответе
(`gitflic mr diff 45 --project mne17let/zloysport --format json`) поле `body`
содержит `&quot;` / `&gt;` / `&lt;` (на этом MR: 84× `&quot;`, 17× `&gt;`, 6× `&lt;`).
CLI отдаёт их без декодирования.

**Фикс:** HTML-unescape (`&quot;`→`"`, `&amp;`→`&`, `&lt;`→`<`, `&gt;`→`>`,
`&#39;`→`'`) для каждой строки `body` перед выводом в pretty-рендере. Особенно
критично для `<`/`>` — в Kotlin/Java дженериках и сравнениях иначе дифф искажается.
Важно: декодировать `&amp;` нужно **последним** (или одним проходом по карте),
чтобы не словить двойное декодирование.

## BUG-002 — `mr diff` (pretty) рендерит заголовок ханка `@@` как одиночный `@`

- **Severity:** Low-Medium (нестандартный unified-diff, ломает copy-paste как патч)
- **Статус:** needs-data — текущий pretty-рендер (`printChanges`) печатает `b.headers` без срезания символов, так что баг либо на стороне API, либо устранён рефактором рендера. Не воспроизводится без доступа к MR #45 в `mne17let/zloysport`. Декодирование entities (BUG-001) теперь применяется и к заголовкам ханков.
- **Найдено:** 2026-06-22, тот же MR #45

**Воспроизведение:**
```bash
gitflic mr diff 45 --project mne17let/zloysport | grep -nE '@ -'
```

**Фактически:**
```
      @ -100,4 +100,5 @@
```

**Ожидается** (стандартный unified-diff hunk header):
```
@@ -100,4 +100,5 @@
```

Открывающий `@@` теряет один `@` (закрывающий `@@` цел). Похоже на баг
форматирования строки ханка в pretty-рендере `mr diff`.

## BUG-003 — `mr diff` (pretty) калечит маркер `\ No newline at end of file`

- **Severity:** Low (косметика)
- **Статус:** needs-data — как и BUG-002: текущий рендер не срезает ведущие символы строк; вероятно, на стороне API или устранено рефактором. Не воспроизводится без MR #45.
- **Найдено:** 2026-06-22, тот же MR #45

**Воспроизведение:**
```bash
gitflic mr diff 45 --project mne17let/zloysport | grep -n 'newline'
```

**Фактически:**
```
      o newline at end of file
```

**Ожидается:**
```
\ No newline at end of file
```

Ведущие `\ N` съедаются (остаётся `o newline...`). Тот же pretty-рендер
`mr diff`, что и в BUG-002.

## BUG-004 — `gitflic mr diff --help` показывает top-level help вместо help подкоманды

- **Severity:** Low (UX; требует подтверждения)
- **Статус:** known-limitation — диспетчер (`lib/gitflic.mjs`) перехватывает `--help`/`-h` на верхнем уровне (флаг `flags.help`) до разбора под-под-команды, поэтому `gitflic mr diff --help` показывает общий usage. Справку по модулю даёт `gitflic mr help`. Полноценный help под-под-команд — отдельная доработка диспетчера.
- **Найдено:** 2026-06-22

**Воспроизведение:**
```bash
gitflic mr diff --help
```

**Фактически:** печатается общий usage верхнего уровня (список всех команд),
а не флаги/опции, специфичные для `mr diff`.

**Ожидается:** help именно по `mr diff` (формат вывода, контекст-строки и т.п.),
как обещает подсказка «run `gitflic <cmd>` for sub-command help».

> Возможно, у `mr diff` просто нет своих флагов и это осознанный fallback —
> нужно подтвердить у автора CLI. Оставляю как needs-confirm.
>
> Подтверждение (2026-06-22): то же на `gitflic mr create --help` — печатается
> top-level usage. Значит баг общий для под-под-команд, не специфичен для `mr diff`.
> Воркэраунд для справки по модулю: `gitflic mr help`.

## BUG-005 — «no token» при залоченном keychain вводит в заблуждение (выглядит как «не залогинен»)

- **Severity:** Low-Medium (UX; ведёт к ложному диагнозу «нет авторизации»)
- **Статус:** open
- **Найдено:** 2026-06-22, при `gitflic mr create` (после серии успешных read-команд в той же сессии)

**Симптом:** в начале сессии `gitflic auth status` / `mr view` / `mr diff` работали
(токен из keychain читался). Позже `mr create` / `user me` / `auth status` стали
отдавать:
```
gitflic: no token. Run `gitflic auth login --token <value>` ...
```
при этом токен из keychain НЕ удалён — keychain просто залочился (таймаут/сон), и
доступ из неинтерактивного контекста вернул ошибку.

**Проблема:** «no token» подразумевает «не залогинен», хотя токен есть, но keychain
недоступен (locked / errSecInteractionNotAllowed). Пользователь идёт перелогиниваться
вместо того, чтобы разблокировать keychain.

**Фикс:** различать «токена нет» и «токен есть, но доступ к keychain не удался».
Во втором случае подсказывать разблокировку keychain (`security unlock-keychain` /
Keychain Access), а не `auth login`.
